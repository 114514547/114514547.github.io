# 从端口冲突到理解 API 网关：一次 AI 反代与生图排障学习记录

这次折腾最初只是一个很具体的问题：我希望在酒馆、萌图工坊和 Cherry Studio 里调用自己能接触到的 AI 模型，尤其是具有生图能力的 Gemini、Nano Banana 和 GPT Image。实际操作后，我先后接触了 gcli2api、Antigravity Gateway、Flow Proxy 和 APS2api，也遇到了端口占用、模型列表不同、后端关闭后 API 失效、Cookie 登录、验证码、429、502 和“服务器繁忙”等问题。

这些错误当时看起来互不相关，但排查下来，它们其实都指向同一件事：我以前把“客户端、反代、上游服务、账号资格和 API 额度”混成了一个概念。这次任务真正让我学到的，不只是怎样填一个 URL，而是一次 API 请求究竟经过了哪些层，以及每一层出了问题时应该看什么。

## 一、我终于理解了前端、后端、网关和上游的区别

酒馆、萌图工坊和 Cherry Studio 属于客户端，也可以理解为前端。它们负责让我选择模型、输入提示词并展示结果，但通常不直接拥有模型算力。

gcli2api、APS2api、Flow Proxy 和 Antigravity Gateway 属于本地后端或网关。它们在电脑上监听一个端口，接收前端发来的 OpenAI 兼容请求，再将请求转换后发送给 Google、OpenRouter 或其他上游服务。

最典型的调用链可以写成：

```text
酒馆 / Cherry Studio / 萌图工坊
        ↓
http://127.0.0.1:端口/v1
        ↓
本地反代或网关
        ↓
Google / OpenRouter / 其他模型提供商
        ↓
响应沿原路返回客户端
```

这里最重要的结论是：**本地 URL 只是入口，不是模型本身。** `127.0.0.1` 指向我自己的电脑；端口则用来区分电脑上不同的服务。后端进程一旦关闭，端口就不再监听，前端自然无法继续调用 API。除非把后端安装成 Windows 服务或设置为开机自启，否则想使用反代时就必须保持它在运行。

## 二、端口冲突为什么会发生

Antigravity Gateway 启动时曾报出下面的错误：

```text
listen tcp 0.0.0.0:8080: bind:
Only one usage of each socket address is normally permitted
```

这并不是模型失效，而是端口 `8080` 已经被其他程序占用。一个 IP 地址上的同一个 TCP 端口，通常只能由一个进程监听。两个反代可以同时运行，但它们必须使用不同端口，例如：

```text
gcli2api                 127.0.0.1:7861
Antigravity Gateway      127.0.0.1:8081
APS2api                  127.0.0.1:2156
Flow Proxy               127.0.0.1:8317
```

因此，“两个反代的 URL 重合”通常不是域名问题，而是监听端口相同。解决方法是修改其中一个服务的 `PORT`、`.env` 或配置文件，并同步修改客户端里的基础 URL。

这次还遇到过 BAT 脚本把说明文字当成命令执行的情况，例如：

```text
'UPSTREAM_BASE_URL' is not recognized as an internal or external command
```

这说明启动脚本本身可能存在换行、编码或命令拼接错误。它和前面的端口冲突是两个独立问题：前者属于脚本层，后者属于网络监听层。排障时不能看到一串错误就把它们当成同一个原因。

## 三、基础 URL 后面的 `/v1` 到底是什么

许多 AI 客户端要求填写类似下面的地址：

```text
http://127.0.0.1:2156/v1
https://openrouter.ai/api/v1
```

其中 `/v1` 一般表示 API 的版本前缀。客户端会在它后面继续拼接具体接口，例如：

```text
GET  /v1/models
POST /v1/chat/completions
POST /v1/images/generations
```

但不同项目对“基础 URL”的约定并不完全一致。有的客户端希望用户填到 `/v1`，有的会自行补全。如果双方都补，可能出现 `/v1/v1/...`；如果双方都不补，则可能请求到不存在的路径。

因此配置一个陌生反代时，不能只问“URL 是什么”，还要同时确认：

1. 客户端选择的是 OpenAI、Gemini 还是 Claude 格式；
2. 基础 URL 是否需要包含 `/v1`；
3. 实际使用的是聊天接口还是 Images API；
4. 反代是否实现了对应接口。

## 四、`pwd`、`sk-...` 和官方 API Key 不是一回事

这是本次任务里最容易误解的一点。

gcli2api 默认使用的 `pwd`，本质上是本地反代的访问密码。APS2api 要求创建一个 `sk-...` 形式的密钥，这把密钥同样主要用于验证“客户端是否有权访问这个本地服务”。前缀长得像 OpenAI Key，不代表它来自 OpenAI，更不代表里面自带费用或模型额度。

OpenRouter 的密钥通常形如：

```text
sk-or-v1-...
```

它才对应 OpenRouter 账户及其余额。Google AI Studio、Vertex AI 或其他官方平台也会有各自的认证方式。虽然客户端经常统一使用下面的请求头：

```http
Authorization: Bearer <key>
```

但 Bearer 后面的字符串究竟只是本地密码，还是连接某个计费账户的真实凭证，取决于服务端如何解释它，而不是取决于它是否以 `sk-` 开头。

所以我现在会把密钥分成三类：

| 类型 | 作用 | 是否直接代表上游额度 |
| --- | --- | --- |
| 本地网关密码，如 `pwd` | 防止别人随意调用本地反代 | 否 |
| 本地生成的 `sk-...` | 以标准形式管理本地访问权限 | 否 |
| OpenRouter 或官方平台密钥 | 关联真实平台账户、余额和计费 | 通常是 |

## 五、为什么经过网关后模型列表变少了

我曾发现：不使用网关时能够看到 Claude 或较新的 Gemini，经过网关后模型列表却不同。这并不一定意味着账号资格消失了。

`GET /v1/models` 返回的不是“世界上所有可用模型”，而是当前网关愿意暴露、能够映射或作者写进列表的模型。模型列表可能受到以下因素影响：

- 网关版本是否更新；
- 上游认证使用的是 GCLI、Antigravity 还是匿名端点；
- 作者是否为新模型加入了名称映射；
- 当前凭证是否有对应权限；
- 客户端是否过滤了不认识的模型类型；
- 模型只支持聊天还是也支持图像输出。

这让我意识到，“模型列表里没有”至少有三种完全不同的可能：上游账号没有资格、网关没有暴露，或者客户端没有正确显示。只有逐层检查才能判断是哪一种。

## 六、订阅资格、网页额度和 API 额度必须分开看

我原先很自然地认为：既然购买了 Google AI Pro，调用 Google 的生图模型就应该消耗 Pro 套餐里的额度。实际情况没有这么简单。

面向消费者的订阅、网页产品额度和开发者 API 计费通常是不同的体系：

```text
Google AI Pro 订阅
    → 主要影响 Gemini、Flow 等消费级产品中的权益

Google AI Studio / Vertex AI API
    → 使用项目、API Key、云端配额或单独计费

OpenRouter Credits
    → 使用 OpenRouter 账户余额，按其模型价格扣费

第三方反代
    → 取决于它实际调用了哪个上游、用了什么凭证
```

反代不会凭空把消费级订阅转换成官方 API 额度。只有当某个工具确实复用了对应产品的登录态或内部接口时，它才可能间接使用网页端资格；但这种方式往往更容易受到风控、验证码、接口变化和服务条款影响。

同样，OpenRouter 中购买的普通 Credits 通常是账户余额，可以用于账户中不同的收费模型，并不天然锁死在 GPT Image 2 上。它与 Google AI Pro 也互不抵扣。

## 七、几次实际失败分别教会了我什么

### 1. 酒馆报 License 错误

酒馆在新建对话后出现 `Chat Completion API` 的产品许可证错误。这说明请求已经到达了某一层服务，但返回错误的未必是我以为的那个模型。错误可能来自网关的上游、错误的接口类型，或者被选中的某个需要授权的组件。

这类错误不能只通过“模型列表能加载”来判断连接正常。`GET /v1/models` 成功，只能证明列表接口可访问；真正的 `POST /v1/chat/completions` 仍然可能失败。因此测试必须至少包含一次真实的最小聊天请求。

### 2. Flow Proxy 不断打开 Google Flow 页面

Flow Proxy 依赖 labs.google 或 Google Flow 的登录态、Cookie 和验证码桥接。浏览器反复打开 Flow 页面，是后端在尝试获得或刷新网页侧需要的身份信息，而不是正常的纯 API 调用体验。

最终测试中，模型列表能够返回 `nano-banana-2`，但额度查询访问 `labs.google/fx/api/auth/session` 超时；实际生图又在 `project.createProject` 阶段返回 HTTP 502。这个案例清楚说明：

> 模型出现在列表里，不等于生图链路可用；登录态有效，也不等于每个内部接口都能稳定访问。

由于这种方式依赖网页内部接口，只要 Google 调整接口、加强验证码或限制访问，反代就可能失效。

### 3. APS2api 提示服务器繁忙

APS2api 的特点是把 OpenAI 兼容请求转换到 Google 匿名端点，并通过 TLS 指纹、验证码处理和节点池提升成功率。它的优势是不必把每次请求都配置成官方付费 API，但匿名端点也意味着更明显的限流和风控。

因此“服务器过于繁忙”可能来自匿名上游容量、节点拥堵、反爬限制或 429 重试，并不代表本地创建的 `sk-...` 密钥余额不足。那把密钥只是进入本地 APS2api 的门票。

### 4. 后端关闭后客户端全部失效

这次在关闭浏览器和所有后端之后，客户端当然无法继续使用本地 API。重新启动 Flow Proxy 后，端口和模型列表恢复，但实际生图仍然失败。这个过程让我建立了一个更严格的测试顺序：

```text
进程是否运行
  ↓
端口是否监听
  ↓
/v1/models 是否返回
  ↓
认证和额度接口是否正常
  ↓
最小聊天或生图请求是否成功
  ↓
最后才测试复杂客户端
```

## 八、几种反代方案应该怎样理解

| 方案 | 主要上游方式 | 优点 | 主要风险或限制 |
| --- | --- | --- | --- |
| gcli2api | Google OAuth、GCLI、Antigravity 凭证 | 支持 OpenAI、Gemini、Claude 格式，多账号和模型映射较完整 | 需要管理凭证，接口变动和账号风控仍可能影响使用 |
| Antigravity Gateway | 通常位于客户端与 gcli2api 之间 | 可以修复或包装响应，提高特定客户端兼容性 | 多一层就多一个端口和故障点，本身不提供模型额度 |
| Flow Proxy | Google Flow 网页登录态和内部接口 | 可以尝试调用 Flow 生图能力 | 强依赖 Cookie、浏览器、验证码和网页内部接口，稳定性较差 |
| APS2api | Google 匿名端点 | 配置方便，有管理后台、节点池、生图和编辑支持 | 容易遇到风控、429、服务器繁忙，不能等同于官方 API |
| OpenRouter | 官方统一 API 网关及账户余额 | 接口规范、模型多、计费明确，客户端兼容性通常最好 | 需要购买余额，具体模型按量收费 |

现在回头看，Antigravity Gateway 和 gcli2api 并不一定互相替代：前者可能是包装层，后者才是实际连接上游凭证的服务。链路越长，兼容性修复的空间越大，但排障复杂度也随之增加。

## 九、我最终更倾向于怎样调用生图模型

如果目标是在 Cherry Studio 中稳定地“对话并生图”，OpenRouter 直连是目前更清晰的路线。典型配置是：

```text
服务商：OpenRouter
基础 URL：https://openrouter.ai/api/v1
API 密钥：自己的 sk-or-v1-... 密钥
```

然后选择真正具有图像输出能力的模型，例如：

```text
google/gemini-3-pro-image
google/gemini-3.1-flash-image
openai/gpt-image-2
```

其中 Nano Banana Pro 更偏向复杂构图、文字渲染和高质量编辑；Nano Banana 2 更强调速度与成本；GPT Image 2 则是另一条成熟的生成与编辑路线。

需要注意，图像输入能力和图像输出能力不是一回事。普通多模态聊天模型可能“看得懂图片”，但不一定能生成图片。判断时应查看模型的 `output_modalities` 是否包含 `image`，并确认客户端调用的是聊天生图模式还是专用 Images API。

## 十、以后遇到反代问题，我会先问这十个问题

1. 当前使用的是哪个客户端？
2. 客户端选择了 OpenAI、Gemini 还是 Claude 格式？
3. 基础 URL 是否正确，是否需要 `/v1`？
4. 对应的后端进程是否正在运行？
5. 端口是否被其他程序占用？
6. `/v1/models` 能否访问？
7. 密钥是本地访问密码，还是实际关联上游账户的凭证？
8. 目标模型只有图像理解能力，还是具有图像生成能力？
9. 当前额度属于消费级订阅、网页产品、官方 API，还是 OpenRouter Credits？
10. 最小真实请求是否成功，而不只是模型列表成功？

## 十一、这次任务真正留下的成长

在这次排障以前，我更关注“应该在输入框里填什么”；现在我会先画出请求链路，判断每一层分别负责什么。

我学会了，端口是本机服务的入口，端口冲突和模型失效是两类问题；本地后端必须保持运行，除非被安装成系统服务；`sk-` 只是字符串格式，不能仅凭外观判断它的来源和额度；模型列表由网关、上游权限和客户端共同决定；消费级订阅不等于开发者 API 余额；能读取模型列表不代表真实聊天或生图一定成功；依赖网页 Cookie 和内部接口的反代虽然可能节省成本，但通常也要承担更高的风控和维护成本。

最重要的是，我开始把错误信息当成“请求在哪一层停下来的证据”，而不是把所有失败都笼统归结为“模型坏了”。这大概就是这次折腾最值得留下来的东西。
